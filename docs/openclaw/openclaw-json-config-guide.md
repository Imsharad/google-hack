OpenClaw Architecture, Configuration, and Runtime Internals: A Comprehensive Technical Report1. Introduction: The Local-First Sovereign Agent ParadigmThe evolution of artificial intelligence has transitioned from centralized, cloud-hosted chat interfaces to autonomous, local-first agents capable of executing complex workflows on host infrastructure. OpenClaw, an open-source framework previously known by development codenames such as Clawdbot and Moltbot, represents the apex of this shift. Unlike traditional Large Language Model (LLM) wrappers that function merely as conversational endpoints, OpenClaw is engineered as a personal AI operating system. It resides on the user's hardware—whether a personal laptop, a dedicated server, or a Virtual Private Server (VPS)—and is granted profound access to the filesystem, terminal, and local network interfaces.This architectural sovereignty offers unparalleled capability: the agent can manage calendars, execute code, reorganize files, and interact with external APIs without data leaving the user's control plane. However, this power necessitates a rigorous configuration framework to ensure stability, security, and predictable behavior. The openclaw.json configuration file serves as the system's DNA, defining everything from network bindings and authentication protocols to the cognitive architecture of memory compaction and sub-agent orchestration.This report provides an exhaustive technical analysis of the OpenClaw ecosystem. It dissects the configuration schema, the bifurcated filesystem architecture distinguishing agentDir from workspace, the intricate logic of the boot-md initialization hook, and the security boundaries enforced by Docker-based sandboxing. Furthermore, it explores the internal mechanisms of memory persistence, specifically the memoryFlush system, and the "fractal agency" model used for sub-agent spawning. The analysis draws upon technical documentation, repository commits, issue trackers, and community runbooks to present a definitive guide for architects and engineers deploying OpenClaw.2. The openclaw.json Configuration SchemaThe central nervous system of an OpenClaw deployment is the configuration file, typically located at ~/.openclaw/openclaw.json. This JSON document governs the behavior of the Gateway (the control plane) and the Agent (the cognitive runtime). In recent versions (v2026.x), the schema has evolved from a nested, session-centric structure to a flattened, root-object hierarchy designed for clarity and modularity.2.1 Schema Overview and Root ObjectsThe configuration file is divided into distinct semantic blocks, each controlling a specific subsystem of the framework. Misconfiguration here is the single most common source of security vulnerabilities.2.2.1 Network Binding (bind)The bind key determines the network interface the gateway listens on. This setting is binary in its security implications:"loopback" (Default/Critical): Binds strictly to 127.0.0.1. The gateway is accessible only from the machine it is running on. This is the only secure default for personal computers not sitting behind a strict firewall. It prevents other devices on the LAN or the public internet from reaching the API."0.0.0.0": Binds to all available network interfaces. This exposes the gateway to the Local Area Network (LAN) and, if port forwarding is enabled, the public internet. While necessary for some remote setups, using this without a VPN or strict firewall allows any attacker who can ping the IP to potentially execute commands via the agent's exec tool."lan": A deprecated or less common setting intended to restrict binding to private IP ranges, though specific implementation varies by version.2.2.2 Authentication and Remote Accessauth.mode: Controls how clients verify their identity."token": Uses a static bearer token. This is standard for CLI operations and local integrations."oauth": Integrates with external identity providers, useful for multi-user enterprise deployments.tailscale: OpenClaw includes native integration with Tailscale for secure remote access.mode: "off" (default) or "on". When enabled, the gateway can be accessed remotely via the Tailnet without exposing ports to the public internet.Implication: This is the recommended pattern for remote access (e.g., accessing your home agent from a phone) as it bypasses the risks of 0.0.0.0 binding.2.3 Agent Defaults: Cognitive ConfigurationThe agents.defaults section defines the baseline behavior for the primary agent and any sub-agents.2.3.1 Model Routing and FallbacksThe framework employs a "Coordinator/Worker" pattern to manage costs and capabilities.model.primary: The ID of the default model (e.g., anthropic/claude-opus-4-6 or ollama/mistral:7b). This model handles the main reasoning loop.model.fallbacks: An array of model IDs. If the primary model fails (rate limits, API outage), the system automatically retries with the next model in the list. This ensures high availability for critical tasks.model.streaming: A boolean flag (true/false). Note that a known issue exists in version 2026.x where this flag is ignored for non-Ollama providers due to a disconnect in the resolveExtraParams function, meaning users cannot easily disable streaming for some local providers.2.3.2 Compaction ConfigurationCompaction is the mechanism by which OpenClaw manages the limited context window of LLMs.compaction.mode: set to "safeguard" to prevent context overflow. This mode actively monitors token usage and triggers summarization before the limit is reached.compaction.reserveTokensFloor: Defines a "safety buffer" of tokens (e.g., 20,000) that are kept free. This ensures that even when the context is "full," there is enough space for the model to generate a response or execute a tool without crashing.2.4 Tool and Capability PoliciesThe tools object defines the "hands" of the agent.web.search: Configures search providers like Perplexity or Brave.enabled: true active the tool.provider: Specifies the backend service.cache: Responses are cached (default 15 mins) to save tokens and costs.exec.safeBins: A security allowlist. It restricts the exec tool (shell execution) to a specific list of binaries (e.g., git, ls, grep), preventing the agent from calling dangerous utilities like dd or rm unless explicitly allowed.Approvals: For sensitive tools (like exec), the system can be configured to require human approval via a Telegram or CLI prompt before execution. This "Human-in-the-loop" mechanism is vital for preventing accidental destruction of data.3. Filesystem Architecture: The Dichotomy of agentDir and workspaceA fundamental architectural concept in OpenClaw is the separation of System State from Cognitive Context. This is realized through two distinct directory structures: the agentDir and the workspace. Confusing these two can lead to configuration errors, particularly regarding authentication and memory persistence.3.1 The Workspace: The "Soul" and Cognitive ContextThe Workspace is the user-facing directory. It contains the data that defines the agent's personality, memories, and high-level instructions. It is designed to be portable; transferring the workspace to another machine effectively transfers the agent's "mind".Default Path: ~/.openclaw/workspace (configurable via agents.defaults.workspace).Role: To provide the "context window" content that makes the agent unique.3.1.1 Core Workspace FilesThe workspace is populated with Markdown files that are injected into the model's context window at the start of every session.SOUL.md: The "Constitution" of the agent. It defines the persona, tone (e.g., "You are a cynical lobster"), and core directives. This file is critical for shaping the "vibe" of the assistant.MEMORY.md: A durable, curated knowledge base. This file contains long-term facts that should never be forgotten (e.g., "The user lives in Chicago," "Project X uses React"). It is distinct from the automated daily logs.AGENTS.md: A registry of other agents or sub-agents the primary agent knows about.TOOLS.md: Documentation on available tools, guiding the model on how to use them.HEARTBEAT.md: Instructions for the background "heartbeat" task, which runs periodically to check for emails or reminders.skills/: A subdirectory containing custom capabilities. Each skill (e.g., a specific API integration) has its own folder and configuration.3.2 The AgentDir: System State and IdentityThe AgentDir is the system-facing directory. It maintains the internal state required for the runtime to function, including authentication credentials and raw session logs. It is generally managed by the OpenClaw daemon rather than the user.Default Path: ~/.openclaw/agents/<agent-id>/agent/.Role: To manage the mechanical and security aspects of the agent instance.3.2.1 Authentication and auth-profiles.jsonThe most critical file in the agentDir is auth-profiles.json. This file stores the API keys and OAuth tokens for the agent.Isolation: Authentication is isolated per agent. If you create a new agent (e.g., researcher), it does not automatically inherit the API keys of the main agent.Configuration: To enable a new agent, administrators often must copy the auth-profiles.json from the main agent's directory to the new agent's directory (cp ~/.openclaw/agents/main/agent/auth-profiles.json ~/.openclaw/agents/researcher/agent/). Failure to do this results in "No API key found" errors.3.2.2 Session TranscriptsWhile summarized memories live in the Workspace, the raw transcripts of conversations live in the AgentDir structure.Path: ~/.openclaw/agents/<agent-id>/sessions/.Format: JSONL (JSON Lines).Content: These files contain the full fidelity of every interaction: user messages, assistant thinking blocks, tool inputs/outputs, and final responses. Unlike Claude Code, which maintains a sidecar index file (sessions-index.json), OpenClaw performs a "deep search" across these JSONL files when recall is requested.3.3 Comparative Architecture: AgentDir vs. WorkspaceFeatureWorkspace (~/.openclaw/workspace)AgentDir (~/.openclaw/agents/<id>/agent)Primary FunctionCognitive Context (Personality, Facts)System State (Auth, Logs, Config)PortabilityHighly Portable (Git-friendly)System-Specific (Contains Secrets/Paths)User Editable?Yes (Markdown files)No (Managed by CLI/Daemon)Key FilesSOUL.md, MEMORY.md, HEARTBEAT.mdauth-profiles.json, sessions/*.jsonlInjection StrategyInjected into System Prompt contextLoaded by Runtime for API callsPersistenceLong-term memory storageSession history storage4. Memory Management Systems: Compaction and FlushOne of the most significant challenges in local AI agents is managing the finite context window of LLMs. OpenClaw addresses this through a sophisticated two-tier memory architecture involving Compaction and Memory Flush.4.1 The Context Window ChallengeAs a conversation progresses, the accumulation of user messages, extensive tool outputs (e.g., reading a file), and assistant responses consumes tokens. When the token count approaches the model's limit (e.g., 128k tokens), the system must "forget" older information to make room for new input. Without a strategy, this results in "lobotomy"—the agent loses critical context established earlier in the session.4.2 The Memory Flush MechanismTo prevent data loss during compaction, OpenClaw implements a memoryFlush system. This acts effectively as a cache write-back mechanism, moving data from ephemeral RAM (context window) to durable storage (disk).4.2.1 ConfigurationThe mechanism is controlled via the agents.defaults.compaction.memoryFlush object in openclaw.json.enabled: Must be set to true (default in some versions).softThresholdTokens: The trigger point. When the session reaches this token count (e.g., 40,000), the flush sequence is initiated.prompt: The specific instruction sent to the model (e.g., "Summarize decisions, current goals, and new knowledge. Reply NO_REPLY if nothing to store.").systemPrompt: A system-level override to enforce the behavior (e.g., "Session nearing compaction. Store durable memories now.").4.2.2 The "Silent Turn" WorkflowWhen the threshold is reached, the runtime injects a "silent turn" into the conversation flow.Injection: The system inserts the memoryFlush.prompt as a user message that is invisible to the actual user.Summarization: The agent processes this prompt, reviewing the recent context to extract key facts.Persistence: The agent writes this summary to a markdown file in the workspace, typically memory/YYYY-MM-DD.md.Compaction: Once the write is confirmed, the system "compacts" the context, deleting the raw message history to free up tokens.Restoration: Because the memory/ directory is part of the context loading sequence (see Section 6), the agent "remembers" the summary of the deleted conversation in subsequent turns.4.3 Technical Constraints and BugsAnalysis of issue trackers reveals a critical bug in the flush logic for certain versions. The shouldRunMemoryFlush function contains deduplication logic that compares the memory flush count to the compaction count. In some implementations, this logic is flawed, causing the flush to fire only on every other compaction cycle. This means that 50% of context compaction events might result in data loss if the bug is not patched or if the user does not manually force memory writes.4.4 Vector Search IntegrationBeyond file-based summaries, OpenClaw utilizes a local vector search engine (SQLite-based with FTS5 and embeddings).Indexing: The system indexes the sessions/*.jsonl transcripts.Retrieval: Agents can use the memory_search tool to perform semantic queries against past sessions. This allows the agent to recall specific details ("What was the API key we generated last week?") that might not have made it into the high-level MEMORY.md summary.5. Runtime Environment: Sandboxing and Isolation StrategyGiven that OpenClaw agents have the capability to execute shell commands (exec), read files, and manipulate the host system, security isolation is paramount. The framework leverages Docker to create sandboxed environments, controlled via the agents.defaults.sandbox configuration.5.1 Docker-Based Isolation ArchitectureThe sandbox does not merely restrict file access; it virtualizes the entire execution environment. When sandboxing is active, tool execution (like bash or python) occurs inside a Docker container rather than on the host OS.Image: Configurable via docker.image. Defaults to openclaw-sandbox:bookworm-slim, a lightweight Debian-based image.Container Prefix: Containers are named with a prefix (e.g., openclaw-sbx-) to allow for easy identification and management via Docker CLI.5.2 Sandbox ModesThe mode key determines the strictness of isolation."off": Tools run directly on the host. This offers maximum capability (the agent can manage your actual desktop files) but poses the highest security risk."non-main" (Hybrid): This is the recommended balance for most users. The "main" session (e.g., the user interacting via CLI) runs on the host. However, sessions originating from secondary sources—such as group chats, sub-agents, or untrusted channels—are forced into the sandbox. This prevents a malicious prompt in a WhatsApp group from executing rm -rf / on the host."all": Every session runs inside a container. This provides maximum security but limits the agent's utility as a "desktop assistant" unless specific host directories are mounted into the container.5.3 Sandbox Scope and LifecycleThe scope key defines the persistence of the container environment."session": Creates a fresh, pristine container for every new conversation. This ensures zero data leakage between sessions but incurs high latency (cold start) as the container spins up for each interaction."agent": A persistent container is assigned to the agent. This allows the agent to install dependencies (e.g., pip install pandas) that remain available for future queries."shared": A single container is shared across multiple agents, optimizing resource usage at the cost of isolation between agents.5.4 Pruning and CleanupTo prevent Docker resource exhaustion, the prune configuration manages container lifecycles.idleHours: Containers are stopped and removed after a set period of inactivity (default 24 hours).maxAgeDays: A hard limit on container lifespan (default 7 days) ensures that environments are periodically reset to a clean state, preventing "configuration drift".6. Lifecycle Hooks: The boot-md MechanismHooks in OpenClaw are event-driven scripts that execute at specific points in the system lifecycle. The boot-md hook is essentially the "BIOS POST" (Power-On Self-Test) for the agent, critical for initialization.6.1 Purpose and ConfigurationThe boot-md hook is enabled in the hooks.internal.entries section of openclaw.json.Trigger Event: gateway:startup. It fires immediately when the gateway daemon initializes.Function: It executes the content of the BOOT.md file located in the workspace.Use Cases:Announcement: "I am online" message to a designated channel.Maintenance: Clearing temporary cache files.Context Priming: Loading specific data into memory before the first user interaction.6.2 Injection Order and Context ConstructionWhile boot-md is an executable hook, its content helps form the initial cognitive state of the agent. The runtime constructs the context window by injecting files in a strict precedence order :System Prompt: The core hardcoded directives of the framework.SOUL.md: Identity and personality (Workspace).MEMORY.md: Durable facts (Workspace).memory/YYYY-MM-DD.md: Ephemeral logs from today and yesterday (Workspace).BOOT.md: Output or directives from the boot hook execution.This order ensures that recent memories (daily logs) and immediate initialization instructions (BOOT.md) take precedence over static identity definitions (SOUL.md) due to the "recency bias" of LLM attention mechanisms.6.3 The "Missing Handler" Bug (v2026.2.x)Technical analysis of issue reports reveals a significant defect in the npm distribution of OpenClaw versions 2026.2.4 through 2026.2.6-3.The Issue: Users executing openclaw hooks list received "No hooks found" despite correct configuration.Root Cause: The build pipeline failed to transpile and copy the handler.ts file for bundled hooks (including boot-md, session-memory, and command-logger) to the dist/ directory. Only the HOOK.md documentation file was present.Implication: On affected versions, the boot-md hook fails silently or throws a "module not found" error, meaning initialization scripts in BOOT.md are never executed.Workaround: Users must downgrade to a stable version, wait for a patch (v2026.2.7+), or manually copy the handler.js files from the source repository to the local dist folder.7. Sub-Agent Orchestration: Fractal AgencyOpenClaw supports a "fractal" agency model, where a primary agent can spawn sub-agents to handle specific tasks (e.g., "Research this topic while I write the email"). This is managed via the sessions_spawn tool.7.1 Spawning Logic and InheritanceWhen a sub-agent is spawned, it is treated as a distinct session with a unique identifier (agent:<id>:subagent:<uuid>). It does not simply clone the parent state; it undergoes a selective inheritance process.7.1.1 Workspace ResolutionInherited: Sub-agents generally inherit access to the parent's Workspace. They receive AGENTS.md and TOOLS.md so they understand the available capabilities.Suppressed: To prevent the sub-agent from assuming the identity of the main assistant, the runtime suppresses SOUL.md, IDENTITY.md, and BOOTSTRAP.md.System Prompt: The sub-agent receives a specialized system prompt focused on "Task Completion" rather than "Personality Simulation." This makes them more robotic and efficient for background work.7.1.2 Authentication InheritanceA common pain point in multi-agent systems is credential management. OpenClaw handles this via fallback logic:Primary Source: The runtime first looks for auth-profiles.json in the sub-agent's own agentDir.Fallback: If credentials are missing, it falls back to the parent agent's profiles. This allows a sub-agent to utilize the main agent's OpenAI key without requiring redundant configuration files.7.2 Sub-Agent QueuesSub-agents operate on a dedicated execution lane (subagent queue). This ensures that heavy background tasks (like scraping a website) do not block the main agent from responding to the user's real-time messages. This concurrency is configurable via agents.defaults.subagents.maxConcurrent (default 8) to prevent API rate limit exhaustion.8. Security and Observability8.1 Network Security: The Binding ImperativeThe most critical security configuration in openclaw.json is the gateway binding.Risk: Binding to 0.0.0.0 exposes the RPC interface to the network. An attacker who can reach this port can send commands to the agent. Since the agent has exec privileges, this is effectively a Remote Code Execution (RCE) vulnerability.Mitigation: Always set gateway.bind to "loopback" (127.0.0.1). For remote access, rely strictly on the tailscale integration or an SSH tunnel, never direct IP exposure.8.2 Path Traversal and CWD VulnerabilitiesThe agent's ability to execute commands is relative to a Current Working Directory (CWD).Vulnerability: Historical vulnerabilities (e.g., GHSA-4mhr-g7xj-cg8j) allowed attackers to inject malicious paths into the CWD parameter, enabling the agent to execute binaries outside the intended sandbox or workspace.Patch: Recent versions sanitize the cwd input and enforce exec.safeBins policies. Administrators should ensure they are running patched versions to mitigate this risk.8.3 Observability and LoggingTo audit agent behavior, OpenClaw provides granular logging controls.Redaction: The logging.redactSensitive key (set to "tools" or "all") uses regex patterns to scrub known secrets (e.g., sk-ant..., xoxb...) from logs before they are written to disk. This prevents openclaw.log from becoming a treasure trove for attackers.Tracing: Enabling observability.enabled writes detailed session traces to a SQLite database (observability.db). This allows for post-incident analysis ("Why did the agent delete that file?") by replaying the decision logic.9. ConclusionOpenClaw offers a robust framework for sovereign AI, but its power is inextricably linked to the complexity of its configuration. The separation of Workspace (cognitive state) from AgentDir (system state) is the foundational concept that enables portability without compromising security. The Memory Flush mechanism solves the context window problem by bridging ephemeral RAM with durable disk storage, though it requires careful tuning to avoid data loss bugs.For the systems architect, the path to a stable OpenClaw deployment lies in:Security First: Enforcing loopback binding and utilizing non-main sandboxing for all external inputs.Configuration Hygiene: Maintaining clean separation between the user-editable Workspace and the system-managed AgentDir.Lifecycle Management: Understanding the boot-md injection order and ensuring handler.ts integrity in the installed distribution.Resource Caps: Tuning compaction.softThresholdTokens and subagents.maxConcurrent to balance performance with API costs.By mastering these elements within the openclaw.json schema, administrators can deploy an AI agent that is not only powerful and autonomous but also secure and reliable.
